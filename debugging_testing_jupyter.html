Debugging & Testing in Jupyter Notebook

// bugs aren't a sign you did something wrong — they're a normal part of the process

Every program breaks sometimes. What separates a frustrating debugging session from a five-minute fix is knowing what kind of broken you're dealing with, and having a repeatable process for narrowing it down. This sheet builds that process, using Jupyter Notebook specifically — including the ways notebooks break in their own special ways.

The Debugging Cycle: Not Guesswork

Debugging means finding, understanding, and correcting an error. The diagram above is a cycle: collect evidence, make one testable explanation, make the smallest useful change, then test the result.

00 Observe, isolate, explain, fix, and verify click to expand +

Changing code randomly and hoping the error disappears is slow and fragile. Instead, work through the five stages below. The BMI example shows how each stage narrows a TypeError into one small, justified fix.

1. Reproduce the problem

First, make the problem happen consistently. Run the program with the same input and record the expected result and the result or error you actually receive. Ask: what input causes it, what did I expect, and what happened instead?

bmi_problem.pypython 3
weight = input("Enter weight: ")
height = input("Enter height: ")

BMI = weight / (height ** 2)
Enter weight: 70 Enter height: 1.75 TypeError: unsupported operand type(s) for ** or pow(): 'str' and 'int'

Because the same input produces the same TypeError, the problem is now reproducible rather than a vague report that it "sometimes fails."

2. Isolate the problem

Most programs contain many lines, but only a small part causes the error. The traceback points to BMI = weight / (height ** 2). Inspect the values involved there before changing anything else.

inspect_types.pypython 3
print(type(weight))
print(type(height))
<class 'str'> <class 'str'>

This sharply reduces the search: the problem is not the formula itself, but the types being passed into it.

3. Hypothesize the cause

Turn the evidence into a testable explanation: input() returns strings, but the BMI calculation requires numeric values. A hypothesis is not a guess; it is the most likely explanation supported by what you observed.

4. Fix the problem

Make the smallest reasonable change that addresses the suspected cause. Here, convert the input text to floating-point numbers at the boundary where it enters the program.

bmi_fixed.pypython 3
weight = float(input("Enter weight: "))
height = float(input("Enter height: "))

BMI = weight / (height ** 2)
print(round(BMI, 2))

float() converts the user's text input into numeric values, allowing division and exponentiation to work as intended.

5. Verify the fix

Run the program again and compare the result with the expected outcome. Then try several reasonable inputs; one successful run is evidence, but it is not strong coverage.

Enter weight: 70 Enter height: 1.75 22.86

Debugging is a cycle

If the program is still broken, do not continue changing code at random. Return to the evidence: reproduce the behavior, isolate the fault more precisely, and revise the hypothesis. A first hypothesis being wrong is normal; each pass should narrow the problem further.

Diagnosis

Types of Errors

Not all bugs announce themselves the same way. Recognizing which category you're in tells you where to even start looking.

02 Syntax, runtime, and logical errors click to expand +
SYNTAX ERROR

Python can't even parse the code — it never runs. Usually a typo: a missing colon, an unclosed bracket. Caught before anything executes.

RUNTIME ERROR (EXCEPTION)

The code is valid Python, but something goes wrong while it's running — dividing by zero, a missing key, a wrong type. Raises a traceback.

LOGICAL ERROR

The code runs fine, no traceback at all — it just gives you the wrong answer. The hardest kind to catch, because nothing complains.

syntax_error.pypython 3
if total > 100
    print("big order")
Cell In[1], line 1 if total > 100 ^ SyntaxError: expected ':'
logical_error.pypython 3
# goal: average of a list of scores

average = sum(scores) / 2   # bug: should divide by len(scores), not 2
print(average)
120.0 # No error at all — but the real average is 80.0, not 120.0. # Nothing will tell you this is wrong except checking the answer yourself.

Jupyter-specific

Out-of-Order Execution

This is the bug category unique to notebooks: the code looks correct, but the order you clicked "Run" doesn't match the order on the page.

04 A live notebook — try running cells out of order click to expand +

This mini notebook has a real kernel state behind it. Click Run on each cell in whatever order you like, and watch what happens.

What just happened

  • Running Cell 2 before Cell 1 raises NameError: name 'x' is not defined — the kernel doesn't know about x yet, regardless of what order the cells appear on the page.
  • Editing Cell 1's code doesn't retroactively change anything — the kernel only updates when you actually re-run that cell. Until then, other cells still see the old value.
  • Restart & Run All wipes the kernel's memory completely and reruns every cell top to bottom — the single most reliable way to confirm your notebook actually works, not just that it worked in whatever order you happened to click things.

Technique

print() Debugging vs. logging

Both let you inspect what's happening while code runs. One is a quick, disposable habit; the other scales to real projects.

05 Same bug, investigated two ways click to expand +
print() DEBUGGING

Fast to add, fast to forget to remove. No record of when or in what order things ran. Fine for a quick check in a notebook cell.

logging MODULE

Timestamped, leveled (DEBUG/INFO/WARNING/ERROR), and can be switched off without deleting a single line. Scales past a single notebook session.

print_debug.pypython 3
def calculate_average(scores):
    print("scores:", scores)          # temporary — easy to forget to delete
    total = sum(scores)
    print("total:", total)
    return total / len(scores)
scores: [80, 90, 70] total: 240
logging_debug.pypython 3
import logging
logging.basicConfig(level=logging.DEBUG)

def calculate_average(scores):
    logging.debug(f"scores: {scores}")
    total = sum(scores)
    logging.debug(f"total: {total}")
    return total / len(scores)
DEBUG:root:scores: [80, 90, 70] DEBUG:root:total: 240 # Change to logging.basicConfig(level=logging.WARNING) later, # and every debug() line goes silent — without touching the function at all.

The function's code is nearly identical either way — the difference is that logging lines can be dialed up or down globally, and carry a timestamp and severity level for free.

Prevention

Handling Errors on Purpose

Sometimes a runtime error is expected — bad user input, a missing file. try/except lets you decide what happens instead of letting the program crash.

else runs only if the try block succeeded with no exception. finally always runs — success, failure, or anything in between — which makes it the right place for cleanup like closing a file.

07 assert statements and a first test click to expand +

assert is a sanity check: if the condition is false, it stops the program immediately with a clear message — much better than finding out three steps later.

assert_demo.pypython 3
discount_rate = 1.5   # bug: this should never exceed 1.0
assert 0 <= discount_rate <= 1, f"Invalid rate: {discount_rate}"
AssertionError: Invalid rate: 1.5

Turning that habit into a test

A test is just an assert (or several) wrapped in a function, run against your real code — so you find out before shipping it, not while running it live.

test_discount.pypython 3
def calculate_discount(price, rate):
    return price * (1 - rate)

def test_calculate_discount():
    assert calculate_discount(100, 0.10) == 90
    assert calculate_discount(200, 0.25) == 150
    print("All tests passed!")

test_calculate_discount()

08 Step-through debugging with pdb / breakpoint() click to expand +

Dropping breakpoint() into your code pauses execution right there and gives you a live prompt to inspect variables — more powerful than sprinkling print() everywhere. Step through this trace to see what a debugger session shows you.

pdb_demo.pypython 3
def apply_bulk_discount(orders):
    total = 0
    breakpoint()  # execution pauses here in a real run
    for price in orders:
        total += price * 0.9
    return total

Polymorphism in Python

// one interface, many types, each doing the "right thing" for itself

You've already used polymorphism — every time you called len() on a list, a string, or a dictionary. This sheet unpacks exactly why that counts, what makes Python's version of it distinctive (duck typing), and how to make your own classes plug into the same interface.

Fig. 1 — one interface, three unrelated implementations, each correct for its own type

Foundation

What Polymorphism Means

Strip away the jargon and it's a simple idea: the same operation works on different types of objects, and each type quietly does the right thing for itself.

01 One function call, several unrelated types click to expand +

Watch the same call, len(...), applied to four completely different kinds of objects:

same_interface.pypython 3
len([10, 20, 30])         # list
len("Python")              # string
len((10, 20, 30))         # tuple
len({"A": 10, "B": 20})  # dictionary
3 6 3 2

A list, a string, a tuple, and a dictionary have almost nothing in common structurally — yet all four understand len(). That's polymorphism: the same interface or operation can work with objects of different types, with each type providing behavior appropriate to itself.

02 Same call, different meaning of "length" click to expand +

Click each type below — notice that "length" doesn't even mean the same thing every time.

click a type above ↑

For a list, length means how many elements. For a string, it means how many characters. For a dictionary, it means how many keys. len() doesn't know or care about that difference — it just asks the object, and the object answers correctly for its own type.

Mechanism

Under the Hood — Each Class's Own __len__()

len() isn't magic. It's a thin, friendly wrapper that calls a special method the object itself defines.

03 len(fruits) conceptually calls fruits.__len__() click to expand +
dunder_len.pypython 3
fruits = ["apple", "banana", "orange"]

print(len(fruits))          # the friendly, everyday syntax
print(fruits.__len__())    # what len() does internally
3 3

Both lines return the same answer, because len(fruits) really is Python calling fruits.__len__() for you. This is also exactly why len() can work on so many different types: each one — list, string, dict, and any class you write yourself — implements its own __len__(), and len() just defers to whichever one is in front of it.

The definition, earned

Why This Qualifies as Polymorphism

Here's the contrast that makes it click: imagine Python didn't have polymorphism for this.

04 One interface vs. a function per type click to expand +

Without polymorphism, you'd need to remember a different function name for every type:

WITHOUT POLYMORPHISM — a function per type
string_length("Python")
list_length([10, 20, 30])
dictionary_length({"A": 1, "B": 2})

Three names to memorize. Add a new type — say, a custom SalesTeam class — and you'd need a fourth function, written from scratch.

WITH POLYMORPHISM — one interface
len("Python")
len([10, 20, 30])
len({"A": 1, "B": 2})

One name, ever. The object's own type determines how its length gets calculated — len() just asks, and trusts the answer.

This is the essence of polymorphism: you don't branch on type yourself with a chain of if isinstance(x, list): ... elif isinstance(x, str): ... — the object already knows how to answer for itself, and the single shared interface makes that invisible to you as the caller.

Python's flavor

Duck Typing

Python takes a specific, lightweight approach to polymorphism — it doesn't check what class an object claims to be. It checks what the object can do.

05 "If it knows how to report its length, len() can work with it" click to expand +

The name comes from an old saying: if it walks like a duck and quacks like a duck, it's a duck — as far as Python is concerned, it doesn't matter what class an object officially belongs to. What matters is whether it supports the behavior being asked of it.

list
string
dict
your own class

None of these four share a common parent class written specifically for "things that have a length." They're unrelated types. len() doesn't require them to be related — it only requires that each one defines __len__(). That's duck typing: Python is asking "can you report your length?", not "are you officially a Sized object?"

Bringing it together

Writing a Polymorphic Class of Your Own

Define __len__() on any class you write, and it immediately plugs into the exact same len() interface as every built-in type.

06 SalesTeam — a custom class that speaks len() click to expand +
sales_team.pypython 3
class SalesTeam:
    def __init__(self, employees):
        self.employees = employees

    def __len__(self):
        return len(self.employees)


team = SalesTeam(["Amy", "Bob", "Carlos"])
print(len(team))
3

SalesTeam now works with the exact same len() interface as lists, strings, tuples, and dictionaries — without inheriting from any of them.

Try it with a second, unrelated class

class ProjectBacklog:
    def __init__(self, tickets):
        self.tickets = tickets

    def __len__(self):
        return len(self.tickets)
click above ↑

SalesTeam and ProjectBacklog share no inheritance whatsoever — one tracks employees, the other tracks tickets. Both plug into len() for exactly the same reason list and string do: each one defines __len__(). That's the whole mechanism.

len() demonstrates polymorphism in Python: the same built-in function works with many different object types because each type can define its own __len__() behavior.

08 Bonus: len() isn't the only one click to expand +

This same pattern — a built-in function or operator calling a dunder method that each type implements for itself — shows up all over Python.

more_polymorphism.pypython 3
str(42)          # calls (42).__str__()
3 + 5            # calls (3).__add__(5)
"a" + "b"        # calls ("a").__add__("b") — totally different behavior, same operator
sorted(team.employees) # relies on each employee name's __lt__() to compare
'42' 8 'ab' ['Amy', 'Bob', 'Carlos']

Notice + on numbers adds, but + on strings concatenates — same operator, different behavior, because int and str each define their own __add__(). It's the identical pattern as len(), just spelled with an operator instead of a function name.

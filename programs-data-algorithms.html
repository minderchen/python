A field guide for Business Analytics with Python

Every program is a shape for your data, plus a set of steps that act on it.

Business analytics work — sales reports, customer segments, revenue dashboards — is really just this equation applied over and over. Get comfortable with it, and reading (or writing) analytics code stops feeling like memorizing syntax.

01

Data structures: shaping your business data

A data structure is just a way of organizing values so an algorithm can work with them. In analytics, you'll live in three shapes: a list of numbers, a record (one row), and a list of records (a table).

a list of numbers
sales = [1200, 950, 1600, 800]
a record (one row of data)
sale = {
    "customer": "Acme Corp",
    "amount": 1200,
    "region": "West",
}
a list of records — this is your "table"
sales = [
    {"customer": "Acme Corp", "amount": 1200, "region": "West"},
    {"customer": "Beta LLC",  "amount": 950,  "region": "East"},
    {"customer": "Acme Corp", "amount": 1600, "region": "West"},
    {"customer": "Delta Inc", "amount": 800,  "region": "East"},
]

Why a list of dictionaries, and not something fancier?▸

A list of dict records is exactly how a spreadsheet or database table looks once it's loaded into Python — each dictionary is one row, each key is a column name. It's plain enough to reason about by hand, but shaped just like what tools such as pandas build on top of once your analysis grows.

The choice of data structure always follows the shape of the real-world thing you're modeling. A single sale is naturally "one record with named fields" — a dictionary. A day's worth of sales is naturally "many of those" — a list.

02

Algorithms: steps that produce an answer

An algorithm is just a sequence of steps for turning your data into an answer: a total, a filtered subset, a ranked list. In analytics, three patterns cover most of the work.

aggregate — total revenue
total = 0
for sale in sales:
    total += sale["amount"]

print(total)
aggregate.py
>>> 4550
flow
filter — West region only
west_sales = [
    s for s in sales
    if s["region"] == "West"
]
print(len(west_sales))
filter.py
>>> 2
sort — biggest sale first
ranked = sorted(
    sales,
    key=lambda s: s["amount"],
    reverse=True,
)
print(ranked[0]["customer"])
sort.py
>>> Acme Corp
Aggregate, filter, sort — why these three cover so much▸

Almost every business question decomposes into one or more of these: "What's our total revenue?" is aggregate. "Which sales were in the West?" is filter. "Who are our top customers?" is sort (usually followed by taking the first few). Chain them and you get real reports: filter to a region, then aggregate, then sort the results.

03

Combining data structures and algorithms

Neither half does anything alone. The data structure holds the shape; the algorithm walks that shape to produce an answer. A real report is just several algorithms run over the same data structure.

def top_customer_in_region(sales, region):
    matches = [s for s in sales if s["region"] == region]
    ranked = sorted(matches, key=lambda s: s["amount"], reverse=True)
    return ranked[0] if ranked else None

print(top_customer_in_region(sales, "West"))
combine.py
>>> {'customer': 'Acme Corp', 'amount': 1600, 'region': 'West'}
Reading this function as "data structure + algorithm"▸

sales is the data structure — unchanged, just passed in. Everything inside the function is the algorithm: filter down to one region, sort what's left, hand back the first (largest) one. The function's name describes the business question; its body is the sequence of steps that answers it.

04

Advanced: grouping and aggregating together

The workhorse of real analytics: revenue by region, orders by customer, counts by category. This nests a dictionary (the data structure) inside a loop (the algorithm) to build up several totals at once.

code
revenue_by_region = {}

for sale in sales:
    region = sale["region"]
    revenue_by_region[region] = (
        revenue_by_region.get(region, 0)
        + sale["amount"]
    )

print(revenue_by_region)
group_by.py
>>> {'West': 2800, 'East': 1750}
watch it accumulate

0
East
0
ready
Why .get(region, 0) instead of revenue_by_region[region]?▸

The first time a region appears, there's no entry for it yet — direct lookup with [region] would raise a KeyError. .get(region, 0) asks for the current total but falls back to 0 if the key doesn't exist yet, so the very first sale for a region still adds correctly instead of crashing.

05

Extending the model: Application = Data + Process + UI

A script that runs once and prints an answer is a program. A tool that other people open, interact with, and get answers back from is an application — and it needs one more ingredient.

Application = Data + Process + UI

Data

The sales records. What the app knows.

+

Process

The algorithms. What the app can compute — filter, aggregate, rank.

+

UI

How a person asks for something, and how the answer comes back.

"UI" doesn't have to mean buttons and windows. In a script, input() and print() already form a minimal UI — a person types a question, the process runs, an answer is printed back.

code — same data, same process, now with a UI layer
def generate_report(sales, region_filter=None):        # Process
    if region_filter:
        sales = [s for s in sales if s["region"] == region_filter]
    total = sum(s["amount"] for s in sales)
    print(f"Report for region: {region_filter or 'All'}")     # UI (output)
    print(f"Total revenue: ${total}")

region = input("Enter region (or press Enter for all): ")  # UI (input)
generate_report(sales, region or None)               # Data passed in
mini_app.py
>>> python mini_app.py
simulated terminal session
Enter region (or press Enter for all): West Report for region: West Total revenue: $2800
Same three-part shape, whether it's a script or a real dashboard▸

Swap input() for a dropdown filter, and print() for a chart on a webpage, and the Data and Process layers barely change — you'd still pass the same sales list into the same generate_report logic. This is why separating the three matters: the UI is the part most likely to change (terminal today, web dashboard tomorrow), while Data and Process stay stable underneath it.

This is also the mental model behind tools like spreadsheets and BI dashboards: a data table underneath, a set of formulas or queries as the process, and charts or filters as the UI layer on top.

Where this goes next▸

The next step for business analytics work is usually swapping hand-built lists of dictionaries for pandas DataFrames — same Data + Algorithm idea, but the data structure gains built-in aggregate, filter, and sort operations (.groupby(), .sort_values()) so you write less of the loop yourself. The mental model here transfers directly.

Data structures hold the shape. Algorithms produce the answer. A UI is just how a person asks the question and hears the answer back.
